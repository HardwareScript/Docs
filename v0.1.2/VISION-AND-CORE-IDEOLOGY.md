## The Design Principles

### 1. Everything Must Be Text-Based

**Why**:
- LLMs excel at text
- Version control works with text
- Humans can read and write text
- No GUI dependency

**Result**: Bring everything together in one language.

### 2. End-to-End in One Language

**The workflow**:
```
Start your ideas
    ↓
Write everything in Hardware Script
    ↓
Compile
    ↓
Give output to fabrication company
```

**No fragmentation. No tool switching. One unified pipeline.**

### 3. 3D Matrix Format (LLM-Native)

**Why 3D matrices**:
- LLMs are very, very good at matrices
- Syntax is very easy to understand
- Humans can write it
- LLMs can excel at using it

**The design**:
- No image-inclined systems
- No external system dependencies
- Everything broken down to text at the lowest level
- Output is in matrix form
- LLMs can fully understand it as executable code
- Like zeros and ones, but in three dimensions

### 4. Deterministic and Reproducible

**Requirements**:
- Same input always produces same output
- Version control friendly
- Git-compatible diffs
- Reproducible builds

**Why this matters**:
```bash
git diff board.hw
```

Should show:
```diff
- Battery @ [1, 10, 10]
+ Battery @ [1, 12, 10]  # Moved 2mm right
```

Not:
```
Binary files differ
```

## The Semantic Boundary: What Hardware Script Actually Designs

### The Precise Definition

After extensive exploration, Hardware Script has hit on the exact philosophical boundary of electronic systems:

**Hardware Script is the master of "Electron Flow and Topology" (The Nervous System and Brain).**

**Hardware Script leaves "Physical Structure, Chemistry, and Acoustics" (The Skin and Bones) to other tools.**

This is not a limitation—it's a precise semantic boundary that keeps the system blazing fast, text-based, and perfectly optimized for AI generation.

### What Hardware Script Designs

```
✅ Electron flow and current paths
✅ Topology and connectivity
✅ Power distribution networks
✅ Signal routing and traces
✅ Component placement and spacing
✅ Electromagnetic behavior
✅ Thermal management (electrical)
✅ Logic gates and control systems
✅ Voltage regulation
✅ Impedance matching
✅ Clock distribution
```

**Everything that makes electrons move purposefully through a system.**

### What Hardware Script Imports

```
⬜ Injection-molded plastic casings
⬜ Chemical compounds (battery electrolytes)
⬜ Acoustic resonance (speaker cones)
⬜ Mechanical gears and linkages
⬜ Optical lens systems
⬜ Pure material science
⬜ Structural engineering
```

**Everything that is purely mechanical, chemical, or acoustic.**

### The Bridge: The .hwm Format

Hardware Script doesn't design the TV casing, but it must obey it.

**The .hwm (Hardware Mechanical) file** is the bridge:

```hw
import "tv_casing.hwm" as Enclosure

define Space "TV_Motherboard":
    dimensions: 300mm × 200mm × 10mm
    
    # Respect mechanical constraints
    obey Enclosure.keep_out_zones
    
    add HDMI_Controller named HDMI1 @ [1, 50, 50]
    
    # The compiler will throw an error if your HDMI port
    # doesn't perfectly align with the hole in the plastic casing!
    constrain HDMI1.connector to Enclosure.hdmi_port_1
```

**The mechanical engineer designs the casing in Blender/SolidWorks.**

**They export a .hwm file defining**:
- Keep-out zones
- Connector alignments
- Screw hole positions
- Thermal vent locations
- Physical constraints

**Hardware Script imports and respects these constraints.**

### Why This Boundary Matters

**By focusing purely on electron flow and topology**, Hardware Script:

1. **Remains text-based** - No need for 3D mesh rendering
2. **Compiles blazingly fast** - No complex geometry calculations
3. **Is LLM-friendly** - AI excels at connectivity and logic
4. **Integrates cleanly** - Works with existing mechanical CAD tools
5. **Avoids bloat** - Doesn't try to be a mechanical modeling tool

**This semantic boundary is what makes the vision achievable.**

### The Complete Product Workflow

**For a complete consumer product (like a TV)**:

```
Industrial Designer (Blender/SolidWorks):
    ↓
Designs the plastic casing, bezel, stand
    ↓
Exports tv_casing.hwm (constraints file)
    ↓
Hardware Engineer (Hardware Script):
    ↓
Imports tv_casing.hwm
    ↓
Designs motherboard, display interconnects, power system
    ↓
Compiler validates alignment with mechanical constraints
    ↓
Exports Gerber files for PCB manufacturing
    ↓
Assembly:
    ↓
PCB + Casing = Complete TV
```

**Two tools, two domains, one integrated product.**

### Examples of the Boundary in Action

**TV Display Panel**:
```
Hardware Script designs: The TFT transistor grid, row/column drivers, power distribution
Mechanical CAD designs: The glass substrate shape, bezel mounting, backlight housing
```

**Solar Panel**:
```
Hardware Script designs: Photovoltaic cell interconnects, busbar routing, junction boxes
Mechanical CAD designs: Aluminum frame, glass encapsulation, mounting brackets
```

**Smart LED Bulb**:
```
Hardware Script designs: LED array, Wi-Fi controller, power supply circuit
Mechanical CAD designs: Glass dome, E27 screw base, heat sink fins
```

**Battery Pack**:
```
Hardware Script designs: Cell interconnects, BMS circuit, current sensing, thermal monitoring
Mechanical CAD designs: Enclosure, cooling channels, mounting brackets
Material Science designs: Lithium-ion chemistry, electrolyte composition
```

**The pattern**: Hardware Script handles the "nervous system," other tools handle the "body."

## Why 3D Matrices Are LLM-Friendly

### The Choice Is Not Arbitrary

The decision to use 3D matrices is deeply connected to LLM capabilities.

**LLMs are trained heavily on**:
- Structured text
- Code
- Arrays
- Tensors
- Mathematical notation

### The Representation

Representing hardware like:
```
[x][y][z] → material states
```

Is actually **LLM-friendly**.

### What This Enables

**For LLMs**:
```
✅ Reasoning about spatial relationships
✅ Editing coordinates programmatically
✅ Generating layout patterns
✅ Understanding diffs
```

**For humans**:
```
✅ Reading coordinates as text
✅ Version controlling changes
✅ Reviewing in pull requests
✅ Debugging with text tools
```

**Without relying on graphical layouts.**

### The Power of Text-Native Geometry

```bash
git diff board.hw
```

Shows:
```diff
- Battery @ [1, 10, 10]
+ Battery @ [1, 12, 10]  # Moved 2mm right

- route Power:
-     - [1, 5, 6]
-     - [1, 15, 6]
+ route Power:
+     - [1, 5, 6]
+     - [1, 15, 8]  # Adjusted Y coordinate
```

**This makes hardware design far easier to automate and collaborate on.**
